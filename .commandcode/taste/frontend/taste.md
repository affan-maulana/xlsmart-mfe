# Frontend

- Architectural stance for frontend platforms: domain-oriented microfrontends that stay independently deployable, with hard boundaries — no Module Federation until genuinely required, no cross-app imports, no centralized BFF, no global state stores, and exactly one shared presentational UI package ("build first, extract later"; duplicated domain code beats a wrongly-abstracted boundary). Confidence: 0.65
- Auth preference for web apps: HttpOnly JWT cookie only, session read and forwarded server-side (BFF converts cookie to `Authorization: Bearer`), zero client-side token access and no `localStorage`/`sessionStorage`. Confidence: 0.6
- Default frontend stack for these projects: Next.js App Router + React 19 + strict TypeScript, pnpm workspaces with a version `catalog`, Turborepo affected-graph CI, Tailwind v4 with shadcn/Radix-style primitives, React Hook Form + Zod (the same schema shared by client form and server route handler), Vitest + Testing Library, Docker `standalone` output behind NGINX sub-path routing. Confidence: 0.6
- Prefers architecture rules encoded as an executable CI check plus an `AGENTS.md`/README documenting them, rather than relying on code review to catch violations. Confidence: 0.55
- Prefers per-app API clients (browser and server) even when the implementation is identical across apps — explicitly said "Do NOT create a shared package yet" and "Only extract into a shared package later if reuse is proven across applications." Same pattern duplicated in each app is preferred over premature shared abstraction for API plumbing. Confidence: 0.75
- Shared package boundaries are strict and contract-shaped: `packages/auth` holds only types (User, SessionUser, NavItem...), session/nav helpers (getSession, requireSession, getNavigation), data mappers, and business-neutral staff metadata (staff_id, location_name, role, permissions) — explicitly "Do NOT put Header / Sidebar / Navigation Components inside packages/auth" and "Do not hardcode these values in each application." Also explicitly bans global state, cross-MFE React Context, Redux, and Zustand: each app independently calls the shared helper to fetch its own session. Confidence: 0.9
- Each app's Next.js `/api/*` route handlers serve as the in-app proxy layer (not a separate BFF application): the browser API client calls a route handler, which reads the HttpOnly cookie and forwards the request to the backend via the per-app `serverApiClient` (adding `Authorization: Bearer`). The architecture chain is Component → Hook → apiClient (browser) → `/api/*` route handler → service (optional) → serverApiClient → backend. A single endpoint per logical operation, not a switch-case proxy. Confidence: 0.85
- Cross-cutting identity gets its own deployable service: in an MFE platform, auth/sign-in/session-cookie issuing belongs in a dedicated app (e.g. `apps/auth`), not embedded in the shell — one owner for credentials, other apps read identity over an HTTP contract instead of duplicating login logic. This holds even when the written spec assigns login to the shell. Confidence: 0.75
- Prefers atomic design (atoms → molecules → organisms) for component organization within feature modules, paired with feature-scoped colocated folders (`_components/`, `_hook/`, `_service/`, `_validation/`) per domain module. Already implemented this pattern with Radix + shadcn/ui in an existing service and wants to preserve it when migrating into the MFE apps. Confidence: 0.6
- Component ownership follows a strict 3-level hierarchy: (1) Feature-Local — used by one feature, stays in the feature folder; (2) App-Level — used by multiple features in the same app, stays in `apps/<app>/components/`; (3) Shared UI — used by multiple apps, moves to `packages/ui`. Business ownership takes priority over Atomic Design classification — an atom with domain logic stays app-level, never moves to the shared package just because it's an atom. Confidence: 0.8
- Prefers formal, descriptive service/app names over abbreviated or jargon shorthand (chose "subscription-management" over the suggested "subscriber-ops"), even when the longer name is less convenient to type. Confidence: 0.65
- Shell chrome preference: the sidebar collapse toggle belongs inside the sidebar itself at its top (directly before the first nav item like Dashboard), not in the header — controls that operate a panel live with that panel. Explicitly corrected a header burger toggle. Confidence: 0.6
- Prefers avatars/profile photos as plain round `next/image` (e.g. `size-10 rounded-full object-cover`) rather than client-only avatar primitives like Radix Avatar, so the photo appears in server-rendered HTML. Explicitly asked for "avatar with round image". Confidence: 0.55
- Accepts duplication of trivial static assets (logo, profile photo) across apps: each MFE keeps its own copy of the image files in `public/images/` wrapped with `withBasePath()`, with no shared-asset mechanism (CDN, shared public dir, asset package) — since the logo is project-wide constant, per-service duplication is cheaper than crossing an app boundary or adding infrastructure. Applies to small brand/static assets, not domain code. Confidence: 0.65
- Centralizes brand asset *path literals* (not the files) as exported constants in the shared package: e.g. `BRAND_LOGO_SRC` / `BRAND_AVATAR_SRC` in `packages/ui/src/brand.ts`; each app still owns its copy of the actual image file and wraps the shared constant with its own `withBasePath()` before passing it to the component — "only the path string is centralized, not the asset files or a CDN/shared-asset mechanism." Confidence: 0.75
- Specifies spacing in UI tweaks as small px ranges (e.g. an 8–12px gap between panels) and expects the value realized through the project's existing design-system spacing scale (Tailwind tokens like `ml-2`/`gap-2`), not ad-hoc pixel values — explicitly asks for the existing spacing system to be used "if available." Confidence: 0.6
- Specifies visual styling with exact values — brand hex colors with gradient angles ("gradient 150degree #1E22AA and #E5005A") and Tailwind token shorthand ("bg muted 50", "ml-4") — and expects them translated verbatim into the matching utility class (e.g. `bg-[linear-gradient(150deg,#1E22AA,#E5005A)]`, `bg-muted/50`). Confidence: 0.6
- When a component uses custom CSS variables or design tokens (e.g. `bg-overlay`, `shadow-overlay`, `rounded-pill`, animation variables), all referenced tokens must be properly defined in `styles.css` — the user notices and reports undefined tokens as broken styling. After fixing one component's missing tokens, expects the agent to proactively audit ALL sibling components in the design system for the same class of issue (cross-referencing every atom component against `styles.css`), rather than waiting for individual breakage reports. Confidence: 0.8
- Prefers using higher-level shared UI wrapper components (e.g. `Modal` from `@repo/ui`) over composing raw Radix primitives (e.g. `Dialog` + `DialogContent` + `DialogHeader` + `DialogTitle`) directly in feature code. Explicitly asked to switch from raw Dialog to the standard `Modal` component to get proper animations and consistent behavior. Confidence: 0.75
- Prefers CSS transitions over keyframe animations for simple open/close state changes (modal fade/scale, overlay fade) — CSS transitions on `data-[state]` attributes avoid the first-frame flash that keyframe animations can cause when Radix applies the state attribute asynchronously. Confidence: 0.7
- Prefers CSS-based positioning and animation solutions over JS-based approaches: explicitly requested `position: fixed; top: 50%; left: 50%; transform: translate(-50%, -50%)` and rejected runtime position calculations, setTimeouts, or layout-effect hacks. Confidence: 0.8
- Modal scroll architecture: expects a strict Header/Content/Footer flex-col structure where Header and Footer are non-scrolling (own padding), and the Content area is the sole scroll container (`flex-1 min-h-0 overflow-y-auto`). The parent DialogContent should have `max-h-[90vh] overflow-hidden` with `gap-0` and no shared padding — each section owns its own spacing. Explicitly said "Do not simply add overflow-y-auto to random elements. Identify which container should actually own the scroll." Confidence: 0.85
- Prefers expanded click targets for interactive elements: when a small control (e.g. checkbox) is inside a list row, make the entire row clickable by adding `role="button"`, `onClick`, and `onKeyDown` (Enter/Space) to the parent container, so the user doesn't need to precisely hit the small control. Combined with `items-center` for vertical centering and `cursor-pointer` for affordance. Confidence: 0.75
