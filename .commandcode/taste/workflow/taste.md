# Workflow

- Drives work from prescriptive spec files committed in the repo (e.g. `docs/mfe-prompt/prompt-0.md`) and asks the agent to "execute prompt N" — expects the agent to read the doc and treat it as the authoritative contract rather than re-ask what it contains. Confidence: 0.7
- Wants tool/command approvals auto-accepted: asked for `cmd --yolo` mid-session, i.e. prefers uninterrupted execution over per-step confirmation. Confidence: 0.6
- Works on the frontend without the dependent backend services up: asked to "bypass login post" so the UI could be browsed while the auth service was down — expects a dev-only escape hatch for any credential/gate that blocks local exploration (previous session had already established: apps must boot and render honest "service unavailable" states when backends are absent, rather than crash). Confidence: 0.55
- Prompts are terse — often a bare verb phrase plus the IDE-open file as the only target ("bypass login post" on `apps/auth/app/api/auth/login/route.ts`, "continue" with just cursor context) — and expect the agent to infer both the resume point and the intended, safe scope of the change without asking for restatement or clarification. Confidence: 0.7
- Expects claims of "done" to be backed by executed verification (builds, tests, runtime smoke checks, negative tests on guards), not just code written — the deliverable summary that closed the session led with evidence. When told to "execute prompt N", the agent should verify every success criterion against the current repo state rather than blindly re-implementing; the user expects the agent to recognize already-complete work. Confidence: 0.6
- Treats a committed spec as a starting point, not a straitjacket: issues one-line structural corrections ("make auth in single service, not in shell") when a boundary looks wrong and expects the written spec, docs and enforcement gates to be amended to match, rather than the correction being rejected for deviating from the document. Confidence: 0.6
