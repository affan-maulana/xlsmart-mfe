# Workflow

- Drives work from prescriptive spec files committed in the repo (e.g. `docs/mfe-prompt/prompt-0.md`) and asks the agent to "execute prompt N" — expects the agent to read the doc and treat it as the authoritative contract rather than re-ask what it contains. Confidence: 0.7
- Wants tool/command approvals auto-accepted: asked for `cmd --yolo` mid-session, i.e. prefers uninterrupted execution over per-step confirmation. Confidence: 0.6
- Works on the frontend without the dependent backend services up: asked to "bypass login post" so the UI could be browsed while the auth service was down, and again asked to ignore session checks in subscription-management to verify service migration — expects a dev-only escape hatch for any credential/gate that blocks local exploration (previous session had already established: apps must boot and render honest "service unavailable" states when backends are absent, rather than crash). Confidence: 0.65
- Prompts are terse — often a bare verb phrase plus the IDE-open file as the only target ("bypass login post" on `apps/auth/app/api/auth/login/route.ts`, "continue" with just cursor context) — and expect the agent to infer both the resume point and the intended, safe scope of the change without asking for restatement or clarification. Confidence: 0.7
- Expects claims of "done" to be backed by executed verification (builds, tests, runtime smoke checks, negative tests on guards), not just code written — the deliverable summary that closed the session led with evidence. When told to "execute prompt N", the agent should verify every success criterion against the current repo state rather than blindly re-implementing; the user expects the agent to recognize already-complete work. Confidence: 0.6
- Treats a committed spec as a starting point, not a straitjacket: issues one-line structural corrections ("make auth in single service, not in shell") when a boundary looks wrong and expects the written spec, docs and enforcement gates to be amended to match, rather than the correction being rejected for deviating from the document. Confidence: 0.6
- Prefers incremental migration over big-bang rewrites: explicitly stated "Avoid big-bang migration" — existing code may temporarily keep its current pattern (e.g. useState forms), new code uses the target pattern (RHF + Zod), and refactored code migrates progressively. Applies when migrating features from standalone codebases into the MFE. Confidence: 0.8
- Treats architecture decision documents as executable contracts: when a user provides a formal "Architecture Decision Update" spec (e.g. component ownership hierarchy, API client rules, auth rules), expects the agent to follow every rule precisely rather than improvising. The spec is the implementation guide, not a conversation starter. Confidence: 0.75
- When migrating features into the MFE, points the agent at the existing standalone codebase (e.g. `../xlsmart-frontend-pre-to-post/`) and expects the agent to inspect, understand, and migrate the relevant module and its dependencies — not rewrite from scratch. Prefers preserving existing patterns (atomic design, component structure) over imposing the MFE's conventions wholesale. Confidence: 0.6
- Expects dev environment to mirror production's same-origin architecture — wants NGINX or docker-compose in front of the dev servers so all apps are reachable under a single origin, not scattered across individual ports. Views dev-prod parity as important for accurate local testing. Confidence: 0.8
- Wants custom startup banner messages in dev commands: requested an informative banner (showing the proxy URL and NGINX status) to print before the dev server starts, implemented as a `dev:banner` script chained before `turbo run dev`. Expects the dev entrypoint to surface clear output rather than silent startup. Confidence: 0.7
- Design-first when building UI chrome: explicitly said "just create dummy sidebar, i want to focus on design" — for shell/header/sidebar work, dummy or mock data is expected and wiring real functionality is deferred until the visuals are settled. Confidence: 0.55
- Specs enumerate explicit scope constraints — "don't change other files unless truly necessary," "preserve existing API/props if possible," "reuse existing components/styling/nav config," "don't add new dependencies or libraries," "don't recreate it elsewhere" — i.e. expects minimal-blast-radius changes that adapt existing code and consumers only when the redesign genuinely requires it; applies even to micro-tweaks (a submenu-gap fix was bounded to "only adjust the horizontal positioning/gap," "do not change its height, width, or vertical positioning," "do not change the main sidebar layout"). Confidence: 0.75
- Writes detailed specs in mixed Indonesian and English (requirements/prose in Indonesian, technical terms and code identifiers in English); expects the agent to follow the spec exactly as written. Confidence: 0.55
- Specifies UI requirements visually: attaches reference screenshots (logo, avatar), sketches desired layout relationships as small ASCII box diagrams (e.g. an 8px gap between a menu panel and its floating submenu), and enumerates elements explicitly — icon types (map-pin, bell), ordering, formats such as staff-id "CRR-2321708", "full width" header — expecting assets and layout to be reproduced exactly as shown. Confidence: 0.55
- Wants documentation pointers for third-party UI libraries in use: asked "is there documentation for these icons?" — expects the agent to identify the library actually installed (e.g. grep package.json for lucide-react) and link the official docs (icon browser + React package usage/props) rather than leaving the user to guess. Confidence: 0.5
- Fine-tunes UI values empirically in the running app: after specifying a spacing range (e.g. an 8–12px submenu gap), tries values in the browser and reports back a different one ("i tried ml-4 is better") — their spec'd range is a starting point, not the final word, and the agent should adopt the tuned value without questioning the deviation, and update any coupled elements (e.g. a hover bridge strip sized to match the gap) alongside it. Confidence: 0.6
- Same-origin local dev via committed NGINX config: a standalone `infra/nginx/dev.conf` (localhost upstreams, /etc/hosts virtual dev domains like `apps.xl.local` and `ucs.xlsmart.local` mapped to 127.0.0.1, reusing the existing `infra/nginx/snippets/proxy.inc`) is preferred over Docker for the dev loop. All app env vars (PUBLIC_APP_URL, AUTH_APP_URL, SHELL_URL, etc.) point to the proxy domain rather than individual app ports so links and redirects stay same-origin. Confidence: 0.75
- Actively edits files in the IDE while the agent works (retunes values, creates new component files mid-task) — expects the agent to re-read a file before every edit, detect and adopt manual changes rather than overwriting them (e.g. keeping the user's own gradient-angle edit, switching to their preferred `ml-4`), and to attribute unrelated in-progress typecheck failures to concurrent work instead of the agent's changes. Confidence: 0.6
- When weighing whether to centralize a cross-app concern (e.g. a shared navigation API), asks for the agent's opinion and explicitly requests concerns ("or do you have another concern?") — expects trade-off reasoning grounded in the repo's architecture rules, and accepts a recommendation that keeps per-app ownership. Confidence: 0.55
- When reporting a UI bug, writes a highly structured spec with markdown headers, numbered investigation checklist, desired behavior, and explicit constraints ("Do NOT add arbitrary setTimeout, delays, or hacks") — expects the agent to follow the investigation order, identify the root cause before making changes, then make the smallest clean fix possible and explain what/where/why. Confidence: 0.85
- Expects the agent to explain the root cause and fix rationale after every bug fix: what caused the issue, which file/component was responsible, what changed, and why the fix prevents recurrence. Confidence: 0.8
